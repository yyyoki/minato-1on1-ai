# 音声対話の設計：「いつ話すか」を中心に

この文書の数値はすべて、調査結果や体験の仮説から置いた初期値です。実際の1on1での効果は未検証です。

## 結論

問うべきは「次に誰が話すか」ではなく、**「今、割って入ってよいか」** です。

- 話さないことを既定にし、条件がそろった瞬間だけ話す
- 話す前に手を挙げ、人が話し続ければ黙って譲る
- 話せなかった内容は捨てず、上司の画面に回す

日本語の日常会話の研究では、話し始めてよい点の検出は専用モデルでも AUC 0.80 前後でした[10]。発話か沈黙かの判断は人間同士でも balanced accuracy 60〜66%（英語データ）という報告があります[15]。完璧な検知を目指すより、**外れたときの被害が小さい設計**にしています。

## 相談への回答

### 1. AIの声を自然にするには

| やること | 理由 | 今回の対応 |
|---|---|---|
| 短く話す | 長いほど機械らしさと割り込み感が増す | 呼びかけ込み40字以内 |
| 最初の一言を事前に合成 | 話し出しの遅れを消す | 「あの、」「えっと、」を面談開始時に合成 |
| 文ごとに合成してつなぐ | 全文合成の待ちをなくし、間を制御できる | 次の文を先読み。呼びかけ後90ms、文間150ms |
| 手を挙げた時点でセリフを合成 | 話し出しの直前に準備を済ませる | 実装済み |
| 止め方をなめらかにする | ブツッと切れると機械的 | 音量を下げてからフェード停止 |
| 声そのものの質 | ここは合成エンジンで決まる | VOICEVOX推奨。本番はクラウドTTSと聞き比べる |

吸気音は効果が確認できず、人の声とかぶるため採用していません。実在の声優の声は複製しません。

### 2. 介入の最適なタイミング

次のすべてを満たしたときだけ声を出します。

1. 上司の発言が確定し、判定が「要介入（中以上）」である
2. その発言が最新で、話者に確信がある
3. 確定後に誰も話し続けていない（累計350ms未満）
4. 句末に応じた無音が続いた
5. 手を挙げてから800ms以上たった
6. 回数の上限に達していない

| 句末 | 必要な無音 | 例 |
|---|---|---|
| 問いかけ | 500ms | 「〜しなかったの」 |
| 言い切り | 700ms | 「〜じゃん」 |
| 判別不能 | 1000ms | |
| 言いさし | 1500ms | 「〜だけど」「〜ので」 |

中リスクは1.3倍待ちます。Zoomは無音を直接測れないため1.5倍待ちます。「けど」で終わる文は話者交替の合図にもなり得るため[13]、禁止せず待ち時間を延ばすだけにしています。

**声の上限（既定「ふつう」）**：90秒以上あけて、30分で5回まで。開始30秒は話しません。設定で「控えめ」（5分以上、30分で3回）に変更できます。

### 3. 発話終了と割り込みの検知

**発話終了**は3つの信号を組み合わせます。

- 音量ベースの音声検出（無音の長さ）
- 句末の形（言い切り、問いかけ、言いさし）
- 音声認識の確定

無音が250ms続いた時点で途中の文を先に判定しておき、確定後の待ち時間を減らします。

**ミナト発話中の割り込み**

| 経過 | 動作 |
|---|---|
| 再生開始〜400ms | スピーカーの回り込み量を学習 |
| 人の声が200ms続く | 音量を25%に下げる |
| 500ms続く | フェードして停止。再開しない |
| 500ms未満で終わる | 相づちとみなし音量を戻す |
| 「はい」など6文字未満の認識文 | 発言として記録するが、止まらない |

ブラウザの声は出力音量を取れないため、認識された言葉が自分のセリフと一致しないときだけ止まります。止まった後に言葉が続かなければ誤検知とみなし、回数を戻して感度を下げます。ミナト自身の声を認識した文は、発言として扱いません。話し終えた後は、ほぼ全文が一致し、かつ人の声が聞こえていないときだけ自分の声とみなします。ミナトの問いの言葉を使って答えた発言を消さないためです。発話と完全に同じ言葉を人が同時に言った場合は、自分の声と区別できません。

### 4. 推奨アーキテクチャ

**今（MVP・追加費用なし）**

```text
マイク ─┬ 音量・声の特徴（ブラウザ内） ──────┐
        └ Chrome音声認識 → 途中文・確定文 ──┤
                                            ▼
                               turn.js（話す／待つ／譲るを決める）
                                 │               ▲
                     判定を依頼   ▼               │ 判定結果
                               FastAPI ─ ローカル判定（＋任意でClaude）
                                            │
                     声：VOICEVOX → Web Audio（音量制御・停止）
```

**本番（対面）の第一候補**

```text
ブラウザ ⇄ WebRTC ⇄ Pipecat
                      ├ Silero VAD ＋ Smart Turn v3（発話終了）
                      ├ 日本語ストリーミングSTT（AmiVoice などを比較）
                      ├ フロア管理（turn.js の考え方を移植）
                      ├ 判定（ローカル＋Claude）
                      └ TTS（VOICEVOX／クラウドを聞き比べ）
```

選定理由：Smart Turn v3 は日本語対応でモデルの利用条件が緩く（BSD-2）、CPUで動きます[3][4]。LiveKit のモデルは LiveKit Agents 専用の条件があります[7]。

**Zoom**：RTMSは受信が中心で、声を会議へ戻す手段は別に要ります[43][44]。当面は、話者が確実に分かる利点を生かし、画面ヒント中心にするのが現実的です。声を出す場合は、ミナト用のPCを参加者にします。

| 段階 | 目的 | 内容 |
|---|---|---|
| 今 | タイミング設計の検証 | この実装で社内リハーサル |
| 次 | 実環境の精度 | 実マイクでログを取り、閾値を調整。AEC済みトラックと端末内認識を検証 |
| 本番 | 遅延と安定性 | Pipecat構成へ移行 |

## 今回の実装

| ファイル | 役割 |
|---|---|
| `static/turn.js` | 話す／待つ／譲るの判断。画面や音声に依存しない |
| `static/audio.js` | 文単位の合成、事前合成、音量制御、フェード停止 |
| `static/app.js` | 判断結果を画面と声で実行する |
| `main.py` | 判定、部下向けセリフ、外部送信の制御、ログの原文除去、アクセス制限 |
| `zoom_bridge.py` | Zoomの「誰かが話している」合図を配信 |
| `tools/test_turn.js` | 会話シナリオの再生テスト |
| `tools/test_judge.py` | 判定、セリフ、ログのテスト |

### 話す内容の変更

従来のセリフは上司への助言で、部下の前で上司の面子を潰す形でした。声は **部下に向けた「上司の意図の推測＋問い」** に変え、上司への提案は画面に移しました。

### 判定の変更

- 謝罪・感謝・気遣いには介入しません（「責任は僕にあるよ、ごめん」など）
- Claudeは既定でオフです。従来は既定モデルが404で、一度も動いていませんでした

## 調整のしかた

`static/turn.js` の冒頭に数値がまとまっています。面談ログの `turn_log` に、発話本文を含めず次の判断が残ります。

| 見るもの | 意味 | 多いときの調整 |
|---|---|---|
| `hint:moved_on` | 話そうとしたが会話が続いた | 問題なければ正常。声が少なすぎるなら `movedOnMs` を確認 |
| `stop:barge` | 話し始めて遮られた | `needMs` を長くする |
| `falseBarge` | 自分の声で止まった疑い | `echoMargin` を上げる |
| `feedback:bad` | 上司が「不要」と判断 | 感度や上限を下げる |
| `speak_gap` | 最後の声から話し出すまで | 長すぎるなら `raiseLeadMs` を短くする |

### Claude判定の実測（2026-11-19）

ローカル判定が反応するテスト用の5文を各設定で1回ずつ送りました。件数が少ないため、傾向の確認にとどまります。

| モデル | 応答時間の中央値（最大） | 2.5秒以内 | 「手伝うよ」等の誤検知への対応 | 1回の費用目安 |
|---|---|---|---|---|
| Opus 5.5 | 4.88秒（7.88秒） | 0/5 | 2件とも介入なしに訂正 | 約1.1セント |
| Sonnet 5.5 | 3.21秒（3.97秒） | 1/5 | 1件は介入なし、1件は画面のみ | 約0.4セント |
| Sonnet 5.5（思考オフ） | 3.63秒（5.71秒） | 0/5 | 同上 | 約0.4セント |
| Haiku 5.5 | 1.84秒（2.50秒） | 4/5 | 1件は誤って声の対象 | 約0.02セント |
| Haiku 5.5（思考オフ） | 1.84秒（2.96秒） | 4/5 | 1件は介入なし、1件は画面のみ | 約0.02セント |

- この結果から、**Claude判定の既定モデルを思考オフのHaiku 5.5にしました**（環境変数 `CLAUDE_MODEL` で変更可）。Claude判定そのものは既定でオフです
- Opus 5.5は判定の質が最も高い一方、2.5秒の制限には収まりませんでした
- Haikuが作ったセリフは安全確認を通らないことがあり、その場合は固定セリフを使います。測定では介入と判定した3件すべてが固定セリフになりました
- 応答が速い構成でも、発話終了後すぐの判定には間に合わない回があります。その場合はローカル判定で進みます

## 認識の速さと区切りの実測

「音声認識の速さ」と「区切り検知の精度」を数値で測る仕組みを追加しました。**実マイクでの計測値はまだ取得していません。** 以下は仕組みの説明で、数値は書いていません。

| 計測 | 内容 | 場所 |
|---|---|---|
| 面談中の自動計測 | 発話ごとに「話し始め→最初の途中文」「話し終わり→確定文」「確定文→判定の完了」「話し終わり→ミナトが話し出す」と、発話の途中で確定した件数を記録 | ふりかえり画面の「音声の計測（実測）」と、面談ログの `metrics` |
| 読み上げ計測テスト | 決まった10文を読み上げ、認識の速さ、1文が複数に割れていないか、確定のあとに声が続いていないか、読んだ文との一致率を測る | スタート画面の「音声の計測テスト」。結果は `logs/measure_*.json` |

- 「話し終わり」は、音量ベースの声の検知で最後に声が出た時刻です。しきい値の影響を受けるため、小声や雑音の多い環境では前後します
- 「間をあけて」と指示した2文（言いさし・言い淀み）で、間に確定してしまうかを見ます。ここが区切り検知の精度に最も近い指標です
- 面談中の自動計測は、マイクで拾った発言だけが対象です。デモ会話、テキスト入力、Zoomは含みません
- 保存するのは時間・件数・一致率・真偽値だけです。発言の本文と読み上げた文は保存しません（サーバー側でも許可した項目以外を捨てます）
- 計測中も、文字起こしのために音声はChromeから外部へ送られます
- 1回の計測は最大10文です。マイク、声の大きさ、ネットワークで変わるため、場所や相手を変えて繰り返して比べてください

実装は `static/metrics.js`（算出）、`static/measure.js`（テスト画面）、`tools/test_metrics.js`（算出の再生テスト）です。
